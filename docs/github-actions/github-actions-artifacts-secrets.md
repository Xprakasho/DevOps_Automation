# GitHub Actions — Artifacts and Secrets

## 1. Why these two concepts matter

In a CI/CD pipeline:

```text
Source Code
    ↓
Build / Test
    ↓
Artifacts ───────────────→ next job / release / download
    ↓
Deployment
```

Secrets solve a different problem:

```text
Workflow
    ↓
Secret / credential
    ↓
Authenticate to AWS / API / registry / service
```

**Artifact = output/data produced by the pipeline.**

**Secret = sensitive value needed by the pipeline.**

Do not confuse them.

---

# 2. GitHub Actions Artifacts

A workflow artifact is a file or collection of files produced during a workflow run. Artifacts can persist after a job finishes and can be shared with another job in the same workflow. Common examples include logs, test results, screenshots, binaries, compressed packages, and coverage output. [GitHub Docs](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts)

Typical flow:

```text
Job A
  |
  | create report.txt
  ↓
upload-artifact
  |
  | GitHub stores artifact
  ↓
Job B
  |
  | download-artifact
  ↓
use report.txt
```

---

# 3. Uploading an Artifact

Our CI pipeline already contains:

```yaml
- name: Create Report
  run: |
    echo "GitHub Actions Artifact Demo" > report.txt
    cat report.txt

- name: Upload Report
  uses: actions/upload-artifact@v4
  with:
    name: demo-report
    path: report.txt
```

The important parts are:

```yaml
name: demo-report
path: report.txt
```

Meaning:

```text
Local runner file:
    report.txt

        ↓ upload

GitHub Actions artifact:
    demo-report
```

The artifact is associated with the workflow run.

---

# 4. Downloading an Artifact

Our second job uses:

```yaml
read-report:
  needs: create-report
  runs-on: ubuntu-latest

  steps:
    - name: Download Report
      uses: actions/download-artifact@v4
      with:
        name: demo-report

    - name: Pipeline Completed
      if: ${{ always() }}
      run: echo "Pipeline completed."
```

The key relationship is:

```yaml
create-report
      ↓
upload artifact
      ↓
demo-report
      ↓
read-report
      ↓
download artifact
```

`needs: create-report` makes the second job wait for the first job.

# 6. Artifact vs Repository File

A normal Git file:

```text
repository
   └── scripts/bash/hello.sh
```

is source code and is version-controlled.

An artifact:

```text
workflow run
   └── demo-report
```

is generated by the workflow.

Think:

```text
Git repository → source/input
Artifact        → generated/output
```

---

# 7. Artifact vs Cache

Do not confuse artifacts with dependency caching.

### Artifact

Used to preserve or share workflow output.

Examples:

```text
test report
build package
logs
coverage report
```

### Cache

Used primarily to speed up repeated jobs by reusing dependencies or other data.

Mental model:

```text
Artifact → "I need this output later."

Cache    → "I want this data again to make the build faster."
```

---

# 8. Artifact Retention

Artifacts do not necessarily remain forever. GitHub has configurable retention behavior; the default storage period for build logs and artifacts is currently 90 days, with repository settings allowing customization subject to GitHub limits. [GitHub Docs](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts)

Therefore:

```text
Artifact
   ↓
stored for retention period
   ↓
eventually expires unless retained according to repository settings
```

For production pipelines, understand the retention policy before treating artifacts as permanent storage.

# 9. GitHub Actions Secrets

Secrets are sensitive values stored for use by workflows.

Examples:

```text
API_TOKEN
DOCKER_PASSWORD
SSH_PRIVATE_KEY
DATABASE_PASSWORD
THIRD_PARTY_TOKEN
```

GitHub supports secrets at different scopes, including:

```text
Repository
Organization
Environment
```

GitHub encrypts secrets before they reach GitHub and injects them into the workflow when explicitly referenced. [GitHub Docs](https://docs.github.com/en/actions/concepts/security/secrets)

---

# 10. Referencing a Secret

Typical syntax:

```yaml
${{ secrets.SECRET_NAME }}
```

Example:

```yaml
- name: Login
  run: some-command
  env:
    API_TOKEN: ${{ secrets.API_TOKEN }}
```

Then the command/script can use:

```bash
echo "$API_TOKEN"
```

Do NOT print the secret.

Bad:

```bash
echo "$API_TOKEN"
```

Even though GitHub attempts to redact secrets in logs, automatic redaction is not a guarantee against every transformation or exposure. GitHub explicitly recommends avoiding plaintext sensitive data and using least privilege. [GitHub Docs](https://docs.github.com/en/actions/reference/security/secure-use)

---

# 11. Secrets Are Not Normal Environment Variables

This:

```yaml
env:
  APP_ENV: Development
```

is a normal workflow variable.

This:

```yaml
env:
  API_TOKEN: ${{ secrets.API_TOKEN }}
```

uses a secret.

Mental model:

```text
APP_ENV
   ↓
normal configuration

API_TOKEN
   ↓
sensitive credential
   ↓
GitHub Secret
```

Do not put credentials directly into:

```yaml
env:
  API_TOKEN: "actual-secret-value"
```

and do not commit credentials to Git.

---

# 12. GITHUB_TOKEN

GitHub automatically provides a `GITHUB_TOKEN` for each workflow job. It is a GitHub App installation access token with permissions limited to the repository containing the workflow. [GitHub Docs](https://docs.github.com/en/actions/concepts/security/github_token)

It can be referenced as:

```yaml
${{ secrets.GITHUB_TOKEN }}
```

GitHub also exposes it through the `github.token` context.

Example:

```yaml
permissions:
  contents: read
```

The important security principle is:

> Give the token only the permissions the workflow needs.

For example, our workflow currently uses:

```yaml
permissions:
  id-token: write
  contents: read
```

This is important because:

```text
contents: read
        ↓
can read repository contents

id-token: write
        ↓
allows the workflow to request an OIDC token
```

The OIDC token is then exchanged with AWS STS to obtain temporary AWS credentials.

---

# 13. Secrets vs OIDC — Important for Our Project

We previously used traditional credentials conceptually:

```text
GitHub
   ↓
long-lived AWS access key
   ↓
AWS
```

Our implemented OIDC design is:

```text
GitHub Actions
      ↓
OIDC token
      ↓
AWS STS
      ↓
AssumeRoleWithWebIdentity
      ↓
temporary AWS credentials
      ↓
AWS API
```

Therefore, for AWS authentication, we do NOT need to store a long-lived AWS access key and secret key in GitHub Secrets.

This is one of the main advantages of our OIDC implementation.

---

# 14. OIDC + Secrets Relationship

OIDC does not mean "we don't need secrets for anything."

It means:

```text
AWS authentication
    ↓
OIDC
    ↓
short-lived credentials
```

Other systems may still require secrets:

```text
GitHub
  ├── AWS → OIDC
  ├── Docker registry → secret/token if required
  ├── External API → secret/token if required
  └── Database → secret if required
```

Use the appropriate authentication mechanism for each system.

# 15. Repository Secrets vs Environment Secrets

### Repository secret

Available to workflows in that repository when referenced and permitted.

Example:

```text
API_TOKEN
```

### Environment secret

Associated with a GitHub Environment such as:

```text
Development
Staging
Production
```

Environment protection rules can require approvals before jobs access environment secrets. [GitHub Docs](https://docs.github.com/en/actions/concepts/security/secrets)

A useful production model is:

```text
Development
   ↓
development secrets

Staging
   ↓
staging secrets

Production
   ↓
production secrets
   ↓
approval/protection
```

This prevents accidentally using production credentials in a development job.

# 16. Secret Security Rules

### Rule 1 — Never hard-code secrets

Bad:

```yaml
env:
  PASSWORD: "mypassword123"
```

### Rule 2 — Never commit secrets

Do not put credentials in:

```text
.yaml
.yml
.tf
.sh
.py
.json
.env
```

and then commit them to Git.

### Rule 3 — Use least privilege

If a credential only needs read access:

```text
READ
```

do not give:

```text
ADMIN
```

GitHub recommends minimum permissions for credentials and workflow tokens. [GitHub Docs](https://docs.github.com/en/actions/reference/security/secure-use)

### Rule 4 — Do not print secrets

Avoid:

```bash
echo "$SECRET"
```

### Rule 5 — Rotate exposed credentials

If a secret is accidentally committed or exposed:

```text
1. Revoke it
2. Rotate it
3. Remove it from the source
4. Investigate where it was exposed
```

Do not assume log redaction makes an exposed secret safe.

---

# 17. Artifact Security

Artifacts are not automatically a safe place for secrets.

Never intentionally upload:

```text
.env
private-key.pem
credentials.json
AWS credentials
database passwords
```

For example, avoid:

```yaml
- uses: actions/upload-artifact@v4
  with:
    path: .
```

unless you know exactly what is being uploaded.

Prefer:

```yaml
- uses: actions/upload-artifact@v4
  with:
    name: deployment-report
    path: report.txt
```

Upload only the files required.

# 19. Interview-Level Definitions

### What is an artifact?

> An artifact is generated output from a GitHub Actions workflow that can be persisted after a job and shared with other jobs or downloaded later.

### What is a secret?

> A secret is sensitive configuration or credential data stored securely by GitHub and exposed to a workflow only when explicitly referenced.

### Artifact vs Secret?

> An artifact is pipeline output; a secret is sensitive input/configuration used by the pipeline.

### Why use OIDC instead of AWS access keys in GitHub Secrets?

> OIDC allows GitHub Actions to obtain short-lived AWS credentials through AWS STS instead of storing long-lived AWS access keys in GitHub Secrets.

### What is GITHUB_TOKEN?

> It is a GitHub-provided, job-scoped authentication token used by workflows to interact with GitHub APIs and repository resources, with permissions controlled by the workflow's `permissions` configuration.
